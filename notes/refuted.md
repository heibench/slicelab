# Refuted

The load-bearing claims that did **not** survive adversarial checking, with the
sharpened version of each.

Twenty claims were handed to verifiers instructed to refute them, to prefer
running a command over reading a document, and to default to `refuted` when they
could not establish the claim. **Sixteen came back changed.** That ratio is the
main reason this project's design differs from the proposal it started as.

Read this before proposing anything that sounds obviously true.

Frozen 2026-09-06. See `README.md` in this directory for provenance and the
one-host caveat.

[prusaslicer-cli] Named GUI presets are addressable on PrusaSlicer 2.9.6 via --printer-profile / --print-profile / --material-profile, all three required together, and they resolve full vendor inheritance from the datadir. The slice.toml [base] design is therefore implementable on this engine with no blocker. -> The claim's first half is right; its characterization of "required" and its "no blocker" conclusion are both wrong. Sharpened:

ADDRESSABILITY AND VENDOR INHERITANCE — CONFIRMED, but only for *system/vendor* presets that the config wizard has actually installed into the datadir. Naming all three of --printer-profile / --print-profile / --material-profile with valid, mutually-compatible system preset names gives exit 0 and a fully resolved config whose values demonstrably come from the vendor `inherits` chain (perimeter_speed = 170 from `*MK4IS_common*`, absent from the named preset's own section).

"ALL THREE REQUIRED TOGETHER" — WRONG ABOUT THE MECHANISM, and the difference is load-bearing. There is no requirement check. Passing any of the six proper non-empty subsets of the three flags makes PrusaSlicer 2.9.6 (Flatpak) die on signal 11: exit 139, zero bytes on stdout AND stderr, deterministically, for every action including `--info`. A driver gets a crash with no message, not a usage error. And the opposite end is worse: passing NONE of the three is accepted at exit 0 and silently yields generic Slic3r built-ins (layer_height 0.3, gcode_flavor reprap, perimeters 3, printer_model empty) — the "defaults trap" the design already names, here as an exit-0 success.

"THEY RESOLVE FULL VENDOR INHERITANCE FROM THE DATADIR" — TRUE ONLY FOR VENDOR-BUNDLE PRESETS. For a user preset file in `<datadir>/print|filament|printer/`, the CLI does NOT follow `inherits` at all: upstream `PresetCollection::load_presets` applies the file's keys onto the *built-in default*, never onto the named parent, and a wholly nonexistent `inherits` target produces exit 0 with zero diagnostics. This is invisible today only because the PrusaSlicer GUI's `Preset::save()` writes the complete key set. It becomes a real, silent, exit-0 corruption the moment slicelab (or CI, or a user, or a hand-edited/older-version preset) supplies a delta-shaped preset — precisely the git-friendly small-delta shape slicelab is built around.

"NO BLOCKER" — OVER-BROAD. Nothing here stops the [base] design, but three things must be designed *for*, not around:
  a. slicelab must always pass all three or none; an incomplete set is a silent SIGSEGV it must translate into a real verdict, and exit 139 with empty streams must never be reported as anything but a fault.
  b. `--query-printer-models` and `--query-print-filament-profiles` — the only machine-readable discovery surface for [base] — exit **1 on complete success**, the same code as "printer profile wasn't found". Their exit code carries no information; the only discriminator is stdout-parses-as-JSON vs stderr-non-empty. A [base] resolver that branches on the exit code cannot tell "enumerated everything" from "that preset does not exist" — a direct instance of the org's silence-reads-as-success failure, sitting on the exact call slicelab needs.
  c. slicelab must never write a delta-shaped preset into a PrusaSlicer datadir and expect `inherits` to compose it. If it materializes presets, it must materialize the full resolved key set, or resolve `inherits` itself and record that it did.

UNVERIFIED: everything above is Flatpak-only. Whether a native (AppImage/distro) PrusaSlicer 2.9.6 shows the same SIGSEGV on a partial profile set, and the same exit-1-on-success for the query actions, was not tested — no native binary is installed on this machine.

[prusaslicer-cli] A single invocation combining --save with --export-gcode yields the G-code and the complete resolved configuration from ONE resolution, with the saved ini and the G-code config footer agreeing on all 373 shared keys (zero differing values). slice.lock's 'all resolved effective settings' field is obtainable as evidence rather than reconstruction. -> Sharpened, with the boundary stated: "In PrusaSlicer 2.9.6, `--save X.ini` and `--export-gcode` in one invocation serialize one and the same in-memory DynamicPrintConfig twice (src/CLI/ProcessActions.cpp v2.9.6: `print_config.save()` at L292-295, the same `print_config` passed to `print->apply()` at L~371). Where the printer profile emits ASCII G-code, the two serializations agree on every key they share — measured 373/373 with zero differing values for MK3S + 0.20mm QUALITY @MK3 + Prusament PLA, and 343/343 with no presets. Four boundaries make the claim as written false:

1. Not 'complete', and not a fixed 373. Each artifact holds keys the other lacks, and the direction flips with configuration: with a vendor preset the ini has 3 keys the footer omits (print_host, printhost_apikey, printhost_cafile — deliberately stripped from G-code, and cleartext in the ini, so the ini must never be committed); with no preset the footer has 4 the ini omits (print_settings_id, printer_settings_id, filament_settings_id, physical_printer_settings_id — precisely the base-preset identity slice.lock wants). 373 is one preset triple's intersection, not a property.

2. The footer does not exist for the MK4/XL family. Those profiles ship binary_gcode = 1, so 2.9.6 writes a GCDE binary container with no text prusaslicer_config block (grep count 0), regardless of a .gcode extension. The G-code-footer half of the cross-check is available only for MK3S-class ASCII output, or by forcing --binary-gcode=0, which changes the artifact the user asked for. A footer-diff run against a binary file reports 'zero differing values' having parsed zero keys — the failure mode the org contract names.

3. It is the resolved input configuration, not 'effective settings'. Auto sentinels and percentages survive into both artifacts: with defaults, both report extrusion_width = 0 and first_layer_extrusion_width = 200% while the toolpaths were generated at 0.45 mm and 0.70 mm — a fact PrusaSlicer emits only as six free-text header comments in a different vocabulary. infill_overlap = 15% and support_material_interface_speed = 80% stay relative even under a preset. Anything slice.lock calls 'effective' still has to be reconstructed or parsed out of prose.

4. It is not evidence that a slice occurred, and the two are not independent. --save executes before the slice block and is not conditioned on it: --scale 20 gives 'All objects are outside of the print volume.', exit 0 (a `return 1` from a bool function upstream), no G-code, and a complete ini on disk. And because both files are dumps of the same object, their agreement is tautological — it corroborates nothing about resolution, it only proves the serializer is deterministic. slicelab should treat the saved ini as the config record, gate it on the G-code artifact actually existing, carry the settings_id keys separately, decode bgcode or record 'footer unavailable — binary G-code' as a value rather than silently comparing nothing, and mark auto/percentage settings as unresolved rather than shipping them under a field named 'effective'."

[gcode-provenance] The PrusaSlicer G-code config footer is the COMPLETE resolved effective configuration (373 keys, identical in value to --save's 376 minus three print-host credential keys), so slice.lock's resolved-settings section can be derived from the artifact rather than reconstructed by a second engine call. VERIFIED for PrusaSlicer 2.9.6 with a full key=value diff. NOT true for OrcaSlicer 2.4.2, where the gcode block and --export-settings each contain keys the other lacks. -> Sharpened, with the boundary the original statement is missing:

For PrusaSlicer 2.9.6, WHEN THE OUTPUT IS ASCII G-CODE, the `; prusaslicer_config = begin/end` footer equals `--save`'s output minus exactly `print_host`, `printhost_apikey`, `printhost_cafile`, byte-identical in value (373 vs 376 keys for the MK4IS, XL5IS and MK3S stock preset trios I ran; md5 of the sorted key=value bodies matches).

It is NOT true in general, and the two places it breaks are the ones slicelab will hit first:

1. Binary G-code. `binary_gcode = 1` is the stock default for the entire current Prusa line (*commonMK4*, *commonXL*, MINI, CORE One, CORE One L in PrusaResearch.ini — the only 5 profiles in the bundle that set the key, none set it to 0). With those presets `--export-gcode -o part.gcode` emits a `GCDE`-magic binary container with NO text config block: `grep -c prusaslicer_config` returns 0 and `strings | grep -c perimeters` returns 0. The 373-key ASCII footer only appeared for MK4IS/XL5IS after I forced `--binary-gcode=0`. Deriving resolved settings from the artifact therefore requires a bgcode decoder that PrusaSlicer's own Flatpak does not ship (/app/bin has no bgcode tool), i.e. a second tool, not merely a second engine call.

2. The key counts and even the DIRECTION of the difference are preset-dependent, so "373/376 minus three printhost keys" cannot be treated as a version-level invariant. With no preset named, the footer has 347 keys and `--save` 343, `--save` emits no printhost keys at all, and the footer is the SUPERSET — it carries print_settings_id, printer_settings_id, filament_settings_id, physical_printer_settings_id, which `--save` omits. Any lock-derivation code that assumes footer ⊆ save, or that assumes a fixed 3-key delta, is wrong for at least one configuration I ran.

Design consequence: slicelab must branch on the container format (check the first four bytes for `GCDE`) and must be able to report "could not tell" when the artifact is binary and no decoder is present — an environment fault, per contract §2.2 — rather than silently returning an empty or partial resolved-settings section. Also note "COMPLETE" is false even in the ASCII case: the three printhost keys are part of the printer preset's effective config and are absent from the footer by design (they are credentials, so excluding them from a lock is right, but the lock should say it excluded them rather than claim completeness).

The OrcaSlicer sentence I could not check: Orca 2.4.2's default-config CLI slice aborts with return -51 before producing either artifact.

[gcode-provenance] "Slicing is deterministic, so a normalized G-code hash is a meaningful identity for a lock file. VERIFIED: exactly one volatile line (the header timestamp) across 3 cube runs and 4 Benchy runs including varied --threads, and stripping it yields identical digests. The load-bearing caveat is that the RAW sha256 proposed in the design is NOT an identity — it differed on every one of 3 runs — and that the normalized hash is sensitive to the input file's basename." -> The claim is true only for the configuration it was tested on, and is stated as a property of "slicing". Sharpened:

PrusaSlicer 2.9.6 is bit-reproducible for the DEFAULT print profile: 8 runs of 3DBenchy differ in exactly one line (the header timestamp), and thread count (1/2/6/12) does not change the output. The raw-sha256 caveat is correct — 5 runs gave 5 distinct raw digests.

But "slicing is deterministic" is FALSE as a general statement, and the failure is not exotic:
- `--fuzzy-skin all`: 8 identical invocations -> 8 distinct normalized digests, 8 distinct filament-used values, differing line counts and print-time estimates.
- `--fill-pattern lightning`: same, 8/8 distinct normalized digests, filament used spanning 4133.78-4136.54 mm.
- `--threads 1` does not restore determinism: fuzzy stays 8/8 distinct; lightning becomes INTERMITTENT (2 distinct digests in 8 runs), which is the worse failure for a lock file — it verifies green repeatedly and then goes red for no authored reason.
- Deterministic across repeats in my runs: adaptivecubic infill, organic supports, ironing. So the property is per-option, not per-engine.

Consequences for the slicelab design, which the original claim understates:
1. A normalized G-code sha256 is NOT an identity in general; it is an identity only for the subset of option-space that happens to be reproducible, and slicelab cannot know that subset a priori.
2. The nondeterminism also poisons the lock's *summary* fields, not just the hash — material and estimated time differ run to run. A lock that records `filament_used` from one run and re-verifies against another is wrong for a reason unrelated to hashing.
3. Per the heibench rule, the lock therefore needs a determinism outcome that a consumer can branch on (e.g. reproducible / nondeterministic / not-established), established by an actual N-run probe, rather than an assumption that a matching hash means "same slice" and a mismatching hash means "something changed". Otherwise a hash mismatch caused by lightning infill is indistinguishable from a real drift in engine version or intent.

Also, two sub-claims are imprecise:
- "including varied --threads" adds no evidence. Varying --threads on the default profile changes nothing, so it is a null test; on the configs that ARE nondeterministic, --threads does not fix it and I could not separate a thread effect from the inherent nondeterminism.
- "the normalized hash is sensitive to the input file's basename" is false as stated. Under the CLI default the basename does not appear in the G-code at all (0 differing lines after renaming; `grep -c -i benchy` = 0). It appears only when `gcode_label_objects` is `firmware`/`octoprint`, in the `; objects_info = ...` JSON line. That setting IS on in Prusa's shipped system presets, so it bites in practice — but it is a settings-conditional property, not a property of the hash.

UNVERIFIED: OrcaSlicer 2.4.2 and SuperSlicer. I could not get Orca's CLI to slice without full presets (exit 205, return_code -51), so nothing in this report supports or refutes determinism for the rest of the engine family.

[orcaslicer] No non-Bambu system profile can be sliced by the OrcaSlicer 2.4.2 CLI as shipped: the compatibility gate matches against `compatible_printers` (a list) which non-Bambu vendor profiles never carry, and its only fallback reads a hardcoded `resources/profiles/BBL/process_full/` directory that OrcaSlicer does not ship — so slicelab's adapter must synthesise the list. -> The claim is true in a narrow case and stated as a universal; the universal is false and the stated mechanism is wrong in two places.

ACCURATE STATEMENT:

Most non-Bambu system profiles slice fine with the OrcaSlicer 2.4.2 CLI as shipped, with no synthesis. 1944 of 2333 (83.3%) non-BBL instantiable process profiles carry their own `compatible_printers`; 47 non-Bambu vendors are entirely unaffected. Verified end-to-end by slicing a cube with unmodified Creality, Sovol and Anycubic system profiles — exit 0, "Success.", real G-code (125/166/133 layers) whose embedded `printer_settings_id` / `print_settings_id` / `printer_model` confirm the requested profiles were actually used.

THE REAL DEFECT, precisely: when a process preset is supplied via `--load-settings`, OrcaSlicer.cpp:2597-2603 takes the `!new_process_name.empty()` branch, which sets `process_compatible` only if the process JSON's OWN `compatible_printers` array literally contains the machine's system name. That branch has no empty-list escape, unlike the 3MF-embedded branch at :2615 which treats an empty list as "compatible with everything". It also does not resolve `inherits` — an Anker child profile whose parent lists the exact machine still fails. Anything else exits with `return_code -17` / "The selected printer is not compatible with the process preset in the 3mf." (shell exit 239).

BOUNDARY: this hits 389 of 2333 non-BBL instantiable process profiles (16.7%) and 0 of 198 BBL. It is a per-file property, not a Bambu/non-Bambu property. Worst affected: Voron 41/41, CoLiDo 27/27, Anker 20/20, Vzbot 18/18, SecKit 7/7, Tronxy 6/6, Vivedino 6/6, DeltaMaker 3/3 (all 100%); Prusa 171/320 (53.4%, includes every MK4S profile); Artillery 36/66; Creality only 32/353 (9.1%).

`resources/profiles/BBL/process_full/` is NOT the gate's fallback. The string is in the binary and the directory genuinely does not ship, but its three source uses (OrcaSlicer.cpp:2412, 2543, 3078) are in the 3MF preset-reload and machine-switch paths; at :2412 a missing directory only logs a warning and keeps the original config. It is irrelevant to the `--load-settings` compat gate.

CONSEQUENCE FOR slicelab: the adapter must inject `compatible_printers` into the process JSON, but only for the ~16.7% of non-BBL profiles that lack their own — and, because inheritance is not resolved, it must inject the flattened value rather than rely on the parent. Note also that thin inherits-based profiles then fail later at -51, so flattening the whole process config (not just this key) is the real requirement. Separately worth recording: Orca is honest here — it never silently succeeds; result.json carries a branchable `return_code` plus `error_string`, and shell exit is nonzero (239 for -17, 205 for -51, 253 for a missing settings file). Consumers must not confuse the negative `return_code` with the shell exit code (exit = 256 + return_code).

[superslicer] "A third adapter is worth building mainly to PROVE the abstraction is not PrusaSlicer-shaped. This is TRUE as a design principle but FALSE for SuperSlicer specifically: SuperSlicer's CLI is PrusaSlicer's CLI (adds only --export-amf and --repair; removes 6 flags; identical --load/--export-gcode/-o/--save), so it applies almost no pressure to the abstraction. OrcaSlicer — already in scope and installed — shares ZERO of those core verbs (no --export-gcode, no -o, no --load, no --save; uses --slice N/--outputdir/--load-settings JSON) and already discharges that job completely. Verified by flag-set diff over all three engines' --help." -> The claim's verifiable numbers are wrong, its stated method could not have been run, and its conclusion is drawn on the wrong axis. Only one sub-part survives.

CONFIRMED: OrcaSlicer 2.4.2 rejects --export-gcode, --load, --save and -o ("Invalid option") and uses --slice/--outputdir/--load-settings. SuperSlicer's --load/--export-gcode(|gcode|g)/--output(|o)/--save are byte-identical in name and alias to PrusaSlicer's.

REFUTED, specifically:
1. "adds only --export-amf and --repair" — SuperSlicer (both 2.5.59.13 stable and master) has SEVEN CLI flags PrusaSlicer 2.9.6 lacks: autosave, cut-grid, cut-x, cut-y, export-amf, export-svg, repair. Six of those seven are not SuperSlicer additions at all — PrusaSlicer 2.8.1 still shipped export-amf, repair, cut-x, cut-y, cut-grid and export-svg and dropped them in 2.9.x. The only flag SuperSlicer genuinely added, against every PrusaSlicer version checked (2.6.1/2.7.4/2.8.1/2.9.6), is --autosave.
2. "removes 6 flags" — the true count is 13 vs PrusaSlicer 2.9.6, 14 vs 2.8.1, 5 vs 2.7.4, 3 vs 2.6.1. Six matches no version. The whole diff is version-dependent and the claim states it version-free; a slicelab adapter targets a version pair, not "SuperSlicer".
3. "Verified by flag-set diff over all three engines' --help" — SuperSlicer is not installed on this machine and no SuperSlicer --help was runnable; that leg of the verification is unsupported. (This is the org's own silence-as-success pattern: a leg that could not run reported as one that ran.)
4. "applies almost no pressure to the abstraction" — measured on the surface slicelab actually abstracts (the config vocabulary the lock must record in full and that [set] overrides address), SuperSlicer 2.5.59.13/master exposes 488 FFF option keys against PrusaSlicer 2.9.6's 349, sharing only 267: 221 SuperSlicer-only, 82 PrusaSlicer-only, i.e. ~45% of the union is unshared. Worse, shared key NAMES carry different value domains — --fill-pattern accepts monotonic and scatteredrectilinear on SuperSlicer and PrusaSlicer 2.9.6 rejects both, while PrusaSlicer accepts alignedrectilinear and zigzag which SuperSlicer's enum lacks.

Where the boundary is: the claim is true only for the ~35 core CLI verbs, and only if you ignore version. On CLI verbs SuperSlicer really does apply near-zero pressure. But that is the cheap axis, and OrcaSlicer's pressure there is LOUD — every wrong verb errors immediately, so an adapter cannot silently mis-map. SuperSlicer applies the opposite and harder kind of pressure: identical verbs, identical preset file format, near-identical key names, and a silently divergent 45% of the option namespace with same-name/different-domain values. That is exactly the case where an adapter can succeed while being wrong, which is the failure mode heibench exists to prevent — so "OrcaSlicer already discharges that job completely" is false: Orca discharges the loud-divergence case only. Whether SuperSlicer is worth a third adapter is a cost question this evidence does not settle, but the "no pressure" premise it was rejected on does not hold.

[fullcontrol] "FullControl is GPL-3.0-only with no linking exception, and slicelab's proposed integration is an in-process import rather than a subprocess — therefore an Apache-2.0 slicelab cannot import it in the same distributable unit." -> The licence half survives; the load-bearing conclusion does not, and the middle premise was never established.

WHAT HOLDS. FullControl's licence file is byte-identical to canonical GPL-3.0 (sha256 3972dc97...), with no exception, no additional permission, no dual-licence offer, and zero SPDX or licence headers in any of its 814 .py files. Nothing grants "or later".

WHERE IT IS IMPRECISE. "GPL-3.0-only" is an inference from absence, not something FullControl states. There is no "only", no "or later", and no per-file grant; the version is asserted solely by README prose ("released under the GPL v3 License", via a link that 404s) and a PyPI trove classifier that maps to neither SPDX -only nor -or-later. GPL-3.0-only is the correct conservative reading, but say "no or-later grant is present, so treat it as GPL-3.0-only" rather than "is GPL-3.0-only". Separately, and relevant to a lock-file tool: the artifact you would actually depend on — fullcontrol-0.1.2-py3-none-any.whl — contains no licence text and no License/License-File metadata field at all, so a lock entry cannot recover the licence from the installed distribution; it must record the classifier or the sdist/repo.

WHAT IS REFUTED — the "therefore". Two independent errors:

(a) "An Apache-2.0 slicelab cannot import it" is false as a licensing statement. Apache-2.0 is one-way compatible with GPLv3 — the FSF's own licence list says of Apache-2.0: "This is a free software license, compatible with version 3 of the GNU GPL." Combining them is permitted. The real obligation is narrower and different in kind: if slicelab conveys a single combined work containing FullControl, that combined distributable must be conveyed under GPL-3.0, while slicelab's own files may remain Apache-2.0 licensed. The correct statement is "slicelab cannot remain effectively Apache-2.0 for a distributable that bundles FullControl", not "cannot import it". (The absolute prohibition the claim describes is Apache Software Foundation *policy* for ASF projects — Category X — which does not bind slicelab.) Also note Apache-2.0 is NOT compatible with GPLv2, which matters if a future adapter targets a GPLv2-only engine.

(b) The import-vs-subprocess line is not the trigger and is not settled. GPL obligations attach on conveying a combined work, not on a user's runtime import. If FullControl is an optional extra the user installs from PyPI, slicelab's own wheel conveys no GPL code and the question of the combined work is the user's, under "mere aggregation". Whether a Python import creates a single combined work is the FSF's stated belief ("we believe they form a single combined program"), not adjudicated law, and subprocess is not automatically safe under that same FSF reasoning either. heibench has already run this experiment: orlab is GPL-2.0-only, imports OpenRocket in-process via JPype, and ships no engine jar (it downloads and caches one at runtime, ORLAB_JAR). It took the GPL as a choice, not because "cannot" applied.

SHARPENED, USABLE FORM. FullControl carries no or-later grant and no linking exception, so treat it as GPL-3.0-only. That does not block slicelab; it constrains one axis — what a single distributable may contain. Three viable shapes, all compatible: (1) FullControl as an optional extra, imported in-process, never vendored, slicelab stays Apache-2.0 and ships no GPL code (the orlab jar pattern, with orlab's licence choice being the conservative rather than the required one); (2) the native backend split into a separate GPL-3.0 package, e.g. slicelab-fullcontrol, leaving the core Apache-2.0; (3) subprocess/IPC isolation, which buys less than the claim implies and costs a process boundary. The claim as written would push the design to (3) or to dropping FullControl, on a premise ("cannot") that is wrong.

FINALLY, THE UNVERIFIED PREMISE. "slicelab's proposed integration is an in-process import rather than a subprocess" is not established anywhere in the brief, which says only "an opinionated interface over FullControl". A licensing conclusion was drawn from an integration mode that has not been decided. Decide the integration mode first; the licence consequence follows from it, not the other way round.

[fullcontrol] "The slicelab surface (geometry in + config delta -> gcode + lock) does not fit FullControl, because FullControl has no geometry input at all (verified: no mesh reader exists) and its entire resolved configuration is 19 scalar settings against PrusaSlicer's 343 (both measured). If this is right, native needs a different verb sharing the lock format; if it is wrong, the adapter pattern extends and the architecture is simpler than I claim." -> The claim's conclusion is wrong, and the architecture consequence it gates ("native needs a different verb") is not established by these facts. Both stated measurements are over-general in the exact trap way: one narrow true fact stated broadly, one source-table constant reported as a resolved-configuration measurement.

What is actually true:
- CONFIRMED, narrowly: FullControl has no MESH reader. No STL/3MF/STEP/OBJ ingest exists anywhere in master @54f2540; its only dependencies are plotly/pydantic/numpy; all STL code writes STL from the toolpath. So "you cannot hand slicelab a part.stl and get FullControl to slice it" is correct and remains a real boundary.
- REFUTED, as stated: "no geometry input at all" is false. `fc.import_design(fc, <file>)` is public API that reads a design's geometry from a JSON file on disk, and I ran geometry-file -> gcode end to end: the file is sha256-able, the transform is deterministic across runs, and gcode built from the file is byte-identical to gcode built from the in-memory design. The slicelab surface shape (hashable geometry artifact in + config delta in -> gcode out, every input and output hashable for a lock) therefore RUNS on FullControl today, unchanged.
- REFUTED: "entire resolved configuration is 19 scalar settings." 19 is `len(base_settings.default_initial_settings)` — a source default table — and only 18 of those 19 are scalars. Measured resolved configuration is 21 keys for `generic`, 22 for `prusa_mk4`, 28 for a Cura-library printer, 29 in union, of which 3 are non-scalar and 2 of those are unbounded lists of gcode-emitting objects (plus eval()-substituted start_gcode/end_gcode for the 662 Cura printers). Add the 28 per-step settable fields across Printer/Extruder/ExtrusionGeometry/Fan/Hotend/Buildplate/StationaryExtrusion/ManualGcode/PrinterCommand, each instantiable unboundedly mid-design. The configuration surface is not small-and-scalar; it is small-and-global plus unbounded-and-positional.
- PrusaSlicer's 343 is real but must carry its command: it is `--save` on 2.9.6. The same install's emitted g-code config block is 349. A lock that says "343 resolved settings" without naming the surface is quoting an ambiguous number.

The sharpened statement the design should lean on instead: FullControl does not fit the slicelab surface as an ADAPTER PEER of PrusaSlicer/Orca, for two reasons neither of which is the ones claimed. (a) Its geometry artifact is a serialized toolpath, not a solid — there is no mesh ingest, so the same part.stl cannot be routed to both a slicer adapter and a FullControl adapter; the geometry input exists but is a different KIND of input. (b) Its design file interleaves configuration with geometry — my design_a.json contained Printer and ExtrusionGeometry steps alongside Points — so "intent delta" and "geometry" are not cleanly separable inputs the way slice.toml and part.stl are, and there is no printer/filament/process preset-with-inheritance layer for a `[base]` stanza to name (the meaningful baseline is one printer module plus its ~21-28 key init dict). That is a genuine argument for a different verb, but it must be made on artifact KIND and intent/geometry separability, not on "no geometry input" or "19 settings" — both of which a reviewer can falsify in one command, and one of which (19) is a constant read out of a source file and presented as a measurement.

[licensing] Subprocess invocation of an AGPL-3.0 slicer does not make slicelab a derivative work, so slicelab's core may be Apache-2.0 (verified only as far as the engines' actual LICENSE files and the absence of any additional clause; the derivative-work conclusion itself is a reasoned position, and both OrcaSlicer's and SuperSlicer's READMEs assert the opposite reading in terms). -> The premises survive; the conclusion does not follow as stated, and the word "so" is where it breaks.

What is established: PrusaSlicer, OrcaSlicer and SuperSlicer are each licensed under an unmodified AGPL-3.0 — all three LICENSE files diff clean against the FSF canonical text except for three http/https URLs, with no §7 additional term. Both installed builds declare AGPL-3.0-only in flatpak metadata. OrcaSlicer's and SuperSlicer's READMEs do assert the "use any part of this software in any way (even behind a web server)" reading; PrusaSlicer's README asserts nothing about license at all, and that sentence appears nowhere in PrusaSlicer 2.9.6.

Where it is over-general: the claim answers the LINKING question and then draws a licensing conclusion that also depends on the COPYING question, which it never reaches. The process boundary governs whether slicelab is a combined/derivative work of the engine at runtime. It says nothing about whether slicelab may REDISTRIBUTE engine-derived material — and slicelab's stated design carries much more engine-derived material than a subprocess call: per-engine adapter option vocabularies, the normalization tables, any bundled option catalogue, and the `[engine.*]` native-option escape hatch all originate in AGPL-3.0 source. prusaslicer-py's own D8 is a decided, enforced precedent that this second question has a different answer from the first: having concluded in D7 exactly what this claim concludes, the same project still had to gitignore PrusaSlicer's `--help` capture and everything derived from it, because shipping it "becomes redistribution the moment it is public". That corpus is verbatim authored prose from the AGPL binary — the typo "tochnology" proves it is copied expression, not fact.

The sharpened, defensible statement: "Reaching an AGPL-3.0 slicer by fork/exec with files and CLI arguments is the FSF's own paradigm of separate programs, so running the engine does not by itself make slicelab a derivative work, and an Apache-2.0 core is available on that axis alone. Two things this does not settle, and neither may be inferred from it: (a) slicelab must ship NO engine-derived corpus — option catalogues, help text, preset bundles, normalization tables built by reading engine source — in an Apache-2.0 distribution; those must be generated on the user's machine at install or run time, per prusaslicer-py D8, or the copyright question is reopened on a copying theory the subprocess argument does not touch. A user-generated slice.lock recording resolved settings values on the user's own machine is not distribution and is not affected. (b) The derivative-work conclusion is a legal position that cannot be verified by any command, is asserted in the opposite direction in terms by two of the three upstream projects' own READMEs, and therefore should be carried in the design as a DECISION WITH AN OWNER and a could-not-tell status, not as an established fact. If the design instead wants to be safe rather than right, licensing slicelab's engine adapters AGPL-3.0 while keeping the engine-agnostic core Apache-2.0 costs little and removes the whole question."

Accurate statement:

[lockfile-design] PrusaSlicer 2.9.6 slicing is byte-deterministic apart from a single header timestamp line, and invariant to thread count — so `output.normalized_sha256` is a sound reproduction key and `slicelab verify` can exist at all. -> The claim is true only for configurations that leave `fuzzy_skin = none`, and it is stated too broadly. Sharpened: **PrusaSlicer 2.9.6 (x86_64 Flatpak, one host) is byte-deterministic apart from the line-1 `; generated by ...` timestamp, and invariant to `--threads` 1/2/3/5/12, for every setting I exercised EXCEPT `fuzzy_skin`.** With `--fuzzy-skin all` the output differs on every single run — 5/5 distinct SHA-256 and 5/5 distinct file sizes even at `--threads 1`, on both an 11 MB 3DBenchy and a 684-byte cube — because `FuzzySkin.cpp` seeds a `thread_local std::mt19937` from `std::random_device` with no run-stable seed (verified in the version_2.9.6 tag source). Derived lock fields move with it: `filament used [mm]` differed by 0.29 mm between two runs of one config.

Consequences for the slicelab design, in order of importance:

1. `output.normalized_sha256` is NOT a sound reproduction key in general. It is sound for a *subset* of the setting space, and slicelab does not currently know where that subset ends. A `slice.lock` that faithfully records `fuzzy_skin = all` among its "ALL resolved effective settings" will still produce a false red on every re-slice. That is a silence-rule inversion in the other direction: `verify` reports "violated" (exit 1, a verdict on the design) for what is actually "could not tell" (exit 2) — the engine is simply not a function of its inputs here.

2. The fix is not to drop the key but to make its applicability a VALUE in the lock, the way orlab exposes `profile_exact`. Something like `output.reproducible: true|false` plus `output.nondeterministic_settings: ["fuzzy_skin"]`, computed from the resolved config before slicing, so `verify` can exit 2 with a reason instead of 1 with a wrong verdict. Do not make this a doc note; a consumer must be able to branch on it.

3. That list must be derived from the engine, not from my one afternoon. I established one member of it by exhausting a handful of likely features; I did not prove the list is complete, and per-engine it will differ — OrcaSlicer and SuperSlicer carry their own fuzzy-skin implementations plus features Prusa lacks, and I tested neither. Treat "the set of nondeterministic settings for engine+version" as a per-version profile fact that has to be measured and re-measured, exactly as the org contract says version facts must be.

4. Even for the deterministic subset, cross-machine/cross-architecture reproducibility remains unestablished — one host, one build, one arch. The claim admits this; it should be carried in the lock as an unproven assumption, not designed around as though it were settled. Nothing I ran either supports or contradicts it.

5. Minor: the timestamp exclusion is real and is exactly one line (line 1). No input path, output path, hostname or user string leaks into the G-code — `grep -E 'scratch|/home/'` on a default slice returns nothing — so a `tail -n +2`-style normalization is sufficient on that axis.

[lockfile-design] The engine silently substitutes unrecognised config values, exits 0, and leaves no trace in the G-code — so the artifact cannot be trusted as a self-describing record of its own resolution, and the lock is not redundant. This is the single claim the lock's justification rests on, and it is also what forces `--config-compatibility=disable` as a non-negotiable default. -> The claim is true only in one narrow corner and is wrong or unestablished everywhere else it is stated.

WHAT IS ACTUALLY TRUE (keep this, it is the real finding): PrusaSlicer 2.9.6 silently DISCARDS an UNRECOGNISED KEY in a config file loaded with `--load`. Exit 0, nothing on stdout or stderr even at `--loglevel 5`, absent from the G-code footer, footer byte-identical to baseline, and `--config-compatibility=disable` does not change this. That single case is real and is enough to defeat "the G-code is a sufficient self-describing record".

WHAT IS WRONG:
- "silently substitutes ... unrecognised config values" — false for the default configuration. The CLI default is `--config-compatibility=enable`, which PRINTS a per-key substitution report (key, loaded value, substituted value) to stdout. Only the non-default `enable_silent` is silent. The claim describes `enable_silent` behaviour as if it were the default.
- Stated as "the engine", it is false for the CLI-override path entirely. `--perimeters=notanumber`, `--gcode-flavor=quantumflavor` and `--frobnicate=1` all exit 1 with a message. Since slicelab's `[set]` delta is exactly CLI overrides, the substitution hazard does not touch slicelab's primary authoring surface at all — only the preset/`--load` path.
- Substitution is not universal even within `--load`: a type error (`perimeters = notanumber`) is fatal, exit 1, regardless of compatibility mode. Only enum-valued keys substitute.
- "leaves no trace in the G-code" — over-broad. The G-code carries all 347 effective settings in `; prusaslicer_config = begin/end`, including the substituted value. What is missing is narrower and should be stated as such: the G-code records WHAT WAS USED, never WHAT WAS ASKED FOR, so requested-vs-resolved deltas, substitution events, and dropped keys are unrecoverable from the artifact.
- "forces `--config-compatibility=disable` as a non-negotiable default" — over-claimed twice. (a) It is a PrusaSlicer-only flag; OrcaSlicer 2.4.2 has no equivalent, so it cannot be a family-wide default for a three-engine tool. (b) It does not close the silent hole the claim is built on: unknown keys still vanish, exit 0, under `disable`. `disable` is still worth defaulting — it converts enum substitution from exit 0 into exit 1, which is the correct three-outcome behaviour — but it must be presented as a partial mitigation of one failure mode, not as the answer.

WHAT SLICELAB SHOULD DO INSTEAD (and what the lock's justification should actually rest on): the reliable detector for a dropped key is not a flag or a log line but a READ-BACK DIFF — slicelab must diff its requested key set against the effective config it reads out of the emitted G-code footer (or `--save`), and report any requested key that is absent or whose resolved value differs as `unsupported`/`degraded` in the lock, not as success. That check subsumes both the silent-key case and the substitution case, works without `--config-compatibility`, and therefore works on OrcaSlicer too. The lock remains non-redundant on independent grounds the claim does not mention: the G-code footer carries no input geometry SHA256, no executable identity beyond the string "PrusaSlicer 2.9.6", no base preset IDs, and no requested-vs-resolved delta.

ALSO UNVERIFIED / FLAGGED:
- Nothing about OrcaSlicer's or SuperSlicer's substitution behaviour was established here; the Orca control run failed too. Do not carry the PrusaSlicer finding across the family without testing it.
- The substitution report is unstructured prose on STDOUT with a broken format string (`loading " << file << "` — the filename is never interpolated, and `loaded = "quantumflavor` has an unbalanced quote). A driver that scrapes it cannot attribute a substitution to a specific `--load` file. This is a genuine upstream defect worth reporting, and it means the message must not be slicelab's only substitution detector.
- Exit codes across the family do not follow the org scheme: PrusaSlicer uses 0/1; OrcaSlicer returned 254 (bad option), 251, 239. Any adapter must map, not pass through.
- G-code is not byte-reproducible: two runs with identical effective config differed only in the `; generated by ... on <UTC timestamp>` header line. A gcode SHA256 in the lock must either exclude that line or be documented as run-unique.

[org-fit] slicelab can honestly populate slice.lock's "ALL resolved effective settings" — TRUE for PrusaSlicer via `--save` (verified: 9957-byte cfg.ini), UNVERIFIED for OrcaSlicer, unknown for SuperSlicer; if an adapter has no equivalent export the lock's central promise degrades to "the settings we sent". -> Refuted as stated, in both directions.

Under-claimed on Orca: OrcaSlicer 2.4.2 DOES export its resolved configuration — `--export-settings file.json`, 624 keys including printer/print/filament preset ids and the engine version, agreeing with the G-code CONFIG_BLOCK to within 4 legacy alias keys, and reflecting undocumented CLI setting overrides. The "adapter with no equivalent export" scenario does not arise for any of the three engines (Prusa `--save`, Orca `--export-settings`, SuperSlicer `--save` present in master source but unverified by execution).

Over-claimed on the thing that matters: neither engine exports "all resolved effective settings". What both export is the complete effective CONFIGURATION DOCUMENT — every option key with preset inheritance and overrides applied. Auto/relative values stay as unresolved sentinels in that document (Prusa: extrusion_width=0 while the toolpaths used 0.45 mm; first_layer_extrusion_width=200%; support_material_interface_speed=80%; deretract_speed=0. Orca: initial_layer_line_width=0; bridge_line_width=100%), and nullable filament overrides are carried alongside the printer values they override with no statement of which won (retract_length=2 recorded next to filament_retract_length=3, G-code emitted G1 E-3). So slice.lock must name the field for what it is — `effective_config` / `resolved_config_document` — and must NOT claim resolved effective values. Calling it "all resolved effective settings" is itself the §2.3 plausible-substitute failure, one level up from the one the claim was worried about.

Three further corrections the lock design must absorb:
- The exported key SET is value-dependent, not a fixed schema (343 / 345 / 376 keys across three PrusaSlicer runs of the same part). A lock diff must tolerate key appearance/disappearance, and hashing "the config" only means anything alongside the engine build.
- PrusaSlicer's `--save` ini OMITS print_settings_id / printer_settings_id / filament_settings_id / physical_printer_settings_id, which the G-code's own config block does carry. If the lock wants base preset identity for PrusaSlicer, it must come from the G-code footer (or from what slicelab itself passed), not from `--save`.
- Capture must be gated on the run, not on the file existing. PrusaSlicer writes a full, ordinary-looking cfg.ini and exits 0 for a slice that produced no G-code; OrcaSlicer writes no settings file at all when the slice fails, and writes one happily when no slicing was requested. So the honest lock rule is: record the config export only when the same invocation produced the G-code the lock hashes, and carry a field (e.g. config_export: captured_with_output | captured_without_output | absent) plus an explicit effective_values_resolved: false. Anything else lets a config document for a slice that never happened read as the record of one that did.

[prusaslicer-py-disposition] "The D9 Flatpak discovery + path translation + sandbox grants generalise to a second engine with only a constant change — proved by subclassing PrusaSlicer as OrcaSlicer and getting correct /app translation and grants. This is what makes 'copy ~90 lines of plumbing, do not depend on the package' viable, and therefore what makes option D work instead of option A." -> The claim is true for two of its three parts and false for the third and for its scope word "only".

Sharpened, verified statement: **Path translation and sandbox grants generalise to a second engine with no change at all — because they are properties of Flatpak, not of PrusaSlicer.** `_to_engine_path` and `_sandbox_grants` are already engine-neutral; the OrcaSlicer subclass got a correct `/app/share/OrcaSlicer/...` rewrite that the engine actually read, and `--filesystem=` behaved identically for both apps. Nothing about those ~47 lines needs an "adapter".

**Discovery does not generalise, and it is not a constant.** Making the subclass discover Orca required two overrides (`FLATPAK_APP_ID` and the `_exec_name()` staticmethod), not one constant. More importantly, `_find_flatpak` hardcodes `--command=<exec>`, which is an *empirical, per-package policy decision*, not a name: for PrusaSlicer the bypass is mandatory because the Flathub entrypoint backgrounds the app and returns exit 0 for a failed invocation (verified: exit 0 vs exit 1); for OrcaSlicer the bypass is unnecessary — the entrypoint execs directly and preserves exit 254 — and applying it silently drops the packager's `LC_NUMERIC=C` workaround. That question had to be re-answered by running the second engine's package, and would have to be re-answered again for SuperSlicer and for every Flathub repackaging. A constant cannot carry it.

**"Proved by subclassing" is too strong.** The subclass is not a working driver: `get_example_shapes()` raises FileNotFoundError (hardcoded `share/PrusaSlicer/shapes`), `slice_model()` fails with rc=254 "Invalid option --export-gcode", and `check_version()` only appears to work because Orca coincidentally also prints its version on line 1 of `--help`. What was proved is narrower: two of the four plumbing methods are engine-neutral; the other two are not.

Consequence for the decision: this does not defeat option D, but it does defeat the reasoning offered for it. The honest version is "the sandbox mechanics (~47 lines) are engine-neutral and copyable verbatim; discovery (~40 lines) is a per-engine, per-package empirical result that must be re-established by running each engine's actual package, and slicelab's adapter layer must own it." Note also that the copied `_to_engine_path` returns the untranslated host path silently when no known Flatpak root matches — a `could-not-tell` presented as a translation, i.e. exactly the failure mode the org contract forbids; it should be fixed on copy rather than inherited (this specific path is code-read, not reproduced — see how_checked (b)).

[slicespec-boundary] "metadata<->gcode correspondence is genuinely independent evidence, not a tautology: a state-modelling scan reproduces PrusaSlicer 2.9.6's own '; filament used [mm]' to a delta of 0.00 mm on five files (absolute-E, relative-E, arc-fitted, extrusion-multiplier, z-offset variants), while two plausible naive scans were wrong by +25.5% and -58.0%. If this were false, the whole 'correspondence' class of slicespec checks would collapse into re-reading the slicer's claims and slicespec's scope would shrink to motion-derived assertions only." -> The measurement is right; the inference is wrong, and the scope is too broad.

Accurate statement: For PrusaSlicer 2.9.6, `; filament used [mm]` is an arithmetic identity over the E values written in the same file — Extruder::extrude() quantizes dE to G-code resolution, accumulates it into m_absolute_E, and returns the very number emitted on the G1 line (Extruder.cpp:33-46, GCodeWriter.cpp:433, GCode.cpp:1469-1485). A correct state-modelling scan therefore CANNOT disagree with it on any file the engine emits, which is why the delta is 0.00 on 11/11 of my variants, not just 5. That is a re-derivation of the slicer's own accumulator, not independent evidence about slicing.

It is still not worthless, but its power domain is different from the one claimed: it is a POST-EXPORT INTEGRITY check. Deleting 201 extrusion moves from an exported file (`sed -i '3000,3200{/^G1 X.* E/d}'`) moved my scan to -74.36 mm / -2.85% against unchanged metadata. So it catches post-process scripts, truncation, transport corruption and hand edits — it does not adjudicate any slicing decision. slicespec should state that scope explicitly rather than sell it as independent corroboration.

And the check must be able to answer "unsupported"/"could not tell" in at least four configurations, all reproduced above: use_volumetric_e=1 (units differ, +140.53%), binary_gcode=1 (zero readable G1 lines while the metadata is still greppable — the exact silence shape), multi-extruder (per-extruder comma list), and any wipe/retraction model where the accumulator gate is not "positive E delta on a move carrying X or Y". Silently emitting a delta in the volumetric or binary case is a plausible-number substitution.

[slicespec-boundary] "The lock does not make slicespec's motion-derived checks circular — it makes them POSSIBLE, because raw motion is uninterpretable without context only the lock carries. Proved by the controlled z_offset pair: 'first extruding Z == first_layer_height' is red on a correct file whenever z_offset != 0, and its correct form 'first_layer_height + z_offset' needs a value that is nowhere in the toolpath. The lock is a check's PREMISE; it may never be cited as its EVIDENCE." -> Two independent failures; the claim is over-general and its stated proof does not hold.

1. "context only the lock carries" is false. Both engines embed their complete resolved configuration in the G-code artifact itself: PrusaSlicer 2.9.6 writes a 349-line `; prusaslicer_config = begin/end` footer containing `first_layer_height` and `z_offset`, present in all five gcode flavors tested and, as a zlib-compressed SlicerMetadata block, in binary .bgcode; OrcaSlicer 2.4.2 writes a 625-line `; CONFIG_BLOCK_START/END` with the same keys. A slicespec check reading only the file it verifies can compute `first_layer_height + z_offset` with no lock present. Worse for the claim: PrusaSlicer's footer is a strict superset of `prusa-slicer --save` output (differs by 4 `*_settings_id` lines), which is precisely where a slicelab lock's "ALL resolved effective settings" would come from — so for this class of check the lock is a CONVENIENCE (single place, hashed, diffable, engine-neutral, and durable if the artifact is post-processed), not an enabler, and it carries no evidence the artifact lacks. If citing the gcode footer is circular, citing the lock's resolved-settings block is exactly as circular; the only non-circular premise is the authored intent (slice.toml) and the base presets on disk.

2. The z_offset pair does not prove the general point, because the claim's own "correct form" is red on correct files. `first extruding Z == first_layer_height + z_offset` holds only when start G-code emits no extrusion. With the stock Prusa MK3S start_gcode (`G1 Z0.2 F720` … `G1 X60 E9 F1000 ; intro line`, hard-coded Z with no z_offset term), PrusaSlicer 2.9.6 at first_layer_height=0.25, z_offset=0.3 gives first extruding Z = 0.2 — neither 0.25 nor 0.55. OrcaSlicer 2.4.2 with the stock MK3S machine profile does the same: z_offset=0.3 shifts object layers 0.2->0.5 but leaves the prime line at Z0.2, so the naive check passes and the "corrected" one fails. The Z of that first extrusion is set by a template string, not by any numeric setting, so no lock field predicts it.

Sharpened statement slicelab can actually lean on: "A motion-derived check needs the engine's resolved configuration as its premise, and that premise is emitted by both PrusaSlicer 2.9.6 and OrcaSlicer 2.4.2 into the G-code artifact itself; the lock's value is that it pins the same facts outside the artifact, in one hashed, engine-neutral, diffable place, not that it makes the check possible. And any check anchored on 'the first extruding move' must be scoped to object extrusion after custom start G-code, or declared unsupported when start G-code extrudes — because `first_layer_height + z_offset` is demonstrably wrong on stock MK3S profiles in both engines."

Unverified by me: SuperSlicer (not installed) and non-Flatpak builds; whether any PrusaSlicer option can suppress the config footer (I found none in --help-fff but did not read the source); and whether the footer stays complete after third-party post-processing scripts, which is a genuine, separate argument for the lock that the claim did not make.


# Blockers

- [gcode-provenance] `output gcode SHA256` as written in the proposal cannot serve as slice.lock's identity. Three runs of an identical slice gave three different digests (cf35d2cf…, 205ad13c…, 6c55c59a…). Every re-slice would dirty the lock in git. The field must become a normalized hash (with the raw hash kept as a separate, explicitly per-file value).

- [gcode-provenance] `result.layers` cannot be populated from PrusaSlicer's output as reported data — PrusaSlicer emits no layer-count field anywhere (grep for 'layer number|total layers|LAYER_COUNT' -> no matches). It is only derivable by counting `;LAYER_CHANGE` markers (100 for the cube, 240 for Benchy). OrcaSlicer does report it explicitly. So the same lock field is engine-reported for one engine and slicelab arithmetic for another; that difference has to be visible or the lock overstates what it knows.

- [gcode-provenance] `result.bounding_box` has no direct source in PrusaSlicer G-code. Only an XY footprint polygon per object (`objects_info`) and `max_layer_z` exist. A `--info` call gives a mesh bbox instead, in the model's own coordinates rather than the plated position (Benchy reports min_x=95, cube min_x=0). Two incompatible bboxes; the field as named is ambiguous and cannot be filled honestly without saying which.

- [gcode-provenance] A line-stripping normalizer is silently wrong for binary G-code. Two `--binary-gcode` runs differed in 5 of 135019 bytes (one timestamp digit at offset 80, plus a 4-byte run at 86-89 that tracks it — a CRC). Normalizing bgcode requires implementing the GCDE container, so `--binary-gcode` output must be `normalized_hash: unsupported` until then.

- [gcode-provenance] `filament_g` cannot be trusted as an engine-reported number. OrcaSlicer emitted `; total filament used [g] = 0.00` for a real 1316.90 mm slice because the profile had `filament_density = 0`. The lock must return unsupported/null in that case rather than record 0.00.

- [gcode-provenance] Deriving the lock from the artifact alone loses engine warnings. A successful (rc=0) sphere slice printed `print warning: Detected print stability issues:` / `Low bed adhesion` / `Consider enabling supports.` on stdout, and `grep -ci 'stability|adhesion|warning' sph.gcode` -> 0. Warnings must be captured at slice time or they are gone.

- [orcaslicer] SuperSlicer is not installed on this machine, so nothing in the proposal's three-engine story is verified for SuperSlicer. Its profile model is PrusaSlicer-descended ini rather than Orca JSON, so the Orca findings here do not transfer to it in either direction.

- [orcaslicer] OrcaSlicer's `--load-settings` cannot consume a GUI-exported profile JSON (missing `type`/`from`), and cannot consume a stock vendor profile (missing `compatible_printers`). The only input form the 2.4.2 CLI reliably accepts is a JSON that slicelab itself synthesises. That is not a blocker to slicelab — it is a blocker to any thinner wrapper — but it means the Orca adapter owns profile construction, not merely argument construction, and slicelab must track Orca's profile-schema requirements per version.

- [orcaslicer] Orca's per-setting CLI override syntax is undocumented in --help and type-sensitive (booleans must use --key=value or they swallow the next argv as a filename). There is no machine-readable key/type catalogue equivalent to prusaslicer-py's --help dump; the only source of the key set is --export-settings output, which gives names and current values but not declared types or enum domains. Deriving those needs either the engine source or per-key probing.

- [superslicer] No preset-by-name CLI in SuperSlicer. `--printer-profile`, `--print-profile` and `--material-profile` do not exist (exit 1, 'Unknown option --printer-profile'); only `--load <ini>` does. slicelab's `[base]` block, as specified, has no SuperSlicer implementation that does not involve slicelab reimplementing PrusaSlicer preset inheritance resolution — forbidden by the org contract's 'do not reimplement the engine's arithmetic' rule. Any SuperSlicer adapter must either answer `unsupported` for `[base]` entirely, or the proposal's `[base]` semantics must be relaxed to 'preset names OR a resolved ini path' per engine.

- [superslicer] No pinnable stable build to lock against. Last stable release is 2.5.59.13 (2024-07-01); the only build carrying the current config surface is prerelease 2.7.62.0-beta2 (2025-11-19). slice.lock's 'engine name + exact build + executable SHA256' would be pinning a beta that upstream may never promote — and 2.5.59.13 is a materially different config surface from the 2.7.62 measurements in this report, so none of these findings transfer to the stable line.

- [superslicer] Engine identity is actively moving. All four active dev branches build as `Slic3r` with `SLIC3R_APP_CMD "Slic3r"` and `SLIC3R_GITHUB "slic3r/Slic3r"`. Binary name, version banner, and the `; SuperSlicer_config = begin` G-code footer marker (which is how effective settings are read back) would all change simultaneously on the next release. There is no way to write a stable adapter against that today, and no announced timeline — slic3r/Slic3r itself has had no commit since 2022-10-28.

- [superslicer] Not packaged for Debian or Ubuntu. Repology lists 35 packaging entries (alt, aosc, aur, gentoo, nix, homebrew, chocolatey, scoop) and none for Debian/Ubuntu; `apt-cache search superslicer` and `flatpak search superslicer` both find nothing. CI would have to curl a GitHub prerelease AppImage by URL. This is a real but SOFT blocker — the AppImage does run directly on Debian 13/glibc 2.41 at exit 0, so it is workable, just unpinnable by package manager.

- [fullcontrol] LICENCE — the hard one. FullControl is GPL-3.0-only (verified from the licence text, the GitHub API, the PyPI classifier and the README, with an explicit adversarial check confirming no 'or later' clause and no per-file headers or linking exception). Because the native backend is an import and not a subprocess, this cannot hide behind a process boundary, exactly as the track brief anticipated. slicelab cannot be Apache-2.0 and import fullcontrol in one unit. This needs a decision recorded in DECISIONS.md before any native code is written. Recommended resolution: keep slicelab core Apache-2.0 (consistent with prusaslicer-py) and ship the native backend as a separate GPL-3.0 optional package.

- [fullcontrol] SURFACE MISMATCH — `geometry in` has no analogue. FullControl cannot read STL, 3MF or any mesh (verified: every 'mesh' hit in the source is the string 'G29 ; mesh bed leveling'). The design IS a Python program, so `slice.toml` cannot carry it and its hash cannot stand in for it. The `slice` verb cannot be made to fit without inventing an input that does not exist.

- [fullcontrol] BASE/DELTA MODEL DEGENERATES — there is no printer/filament/process preset triple and no inheritance graph, only a single printer-profile axis of 19 scalar settings. The gap between 'small authored delta' and 'huge hidden resolved truth' that justifies the lock for a slicer is roughly absent here (19 keys vs 343). The `[base]` and `[engine.*]` sections have no meaningful analogue.

- [fullcontrol] NOT A BLOCKER BUT MUST BE DESIGNED AROUND — FullControl silently drops misspelled settings (reproduced: nozzle_temp typo yields 210 C instead of the requested 215 C, exit 0), silently falls back to the 'generic' profile with only a printed warning, calls bare `exit()` on its plot-path error (reproduced: exit code 0), and can emit a zero-extrusion print with no warning. slicelab must supply the honesty layer; it cannot inherit one.

- [licensing] Nothing makes the proposal impossible. The single hard constraint is the FullControl backend: it cannot be an in-process import inside an Apache-2.0 slicelab distribution, and a pip extra does not fix that. It must be a separately distributed GPL-3.0 package (or reached across a subprocess boundary slicelab builds itself, since FullControl ships no CLI — its pyproject.toml declares no [project.scripts]).

- [licensing] Caching or redistributing Prusa profile bundles fetched from the CURRENT update channel is blocked as stated: prusa3d/PrusaSlicer-settings-prusa-fff has no LICENSE file anywhere in its 161 paths (git trees API, recursive=1, truncated: False), so there is no grant to rely on. The workaround is available and verified — the same bundle inside the AGPL-covered application is byte-identical (sha256 a6155d92471d3b0ae11bed051bb04a4c1157fd6b05fef22416eafd12bce9c839) — but slicelab must source from the installed application's resources directory and record that it did.

- [licensing] Committing lock files or test fixtures containing resolved vendor settings into an Apache-2.0 slicelab repository is blocked; prusaslicer-py already hit this and resolved it in D8 (generate locally, gitignore, hand-author a synthetic fixture). Any CI that wants an end-to-end lock must generate it at runtime, and per D8's own reasoning the tests that consume it must SKIP loudly when it is absent rather than pass vacuously.

- [lockfile-design] Cross-machine and cross-architecture determinism is NOT established. Every determinism measurement here is one x86_64 machine, one Flathub build, one GNOME 50 runtime. If PrusaSlicer's floating-point path differs across CPUs, libm versions, or the Windows/macOS builds, then `output.normalized_sha256` is machine-local and `slicelab verify` on a colleague's laptop reports exit 1 (violated) for an environment difference — a false red, which is the silence rule inverted. This must be measured on a second machine BEFORE the lock's output hash is treated as a portable check; until then `verify` should default to tier 1 (config re-resolution) and require an explicit tier-2 request. There is no honest way to design around this by reasoning; it needs a second machine.

- [lockfile-design] OrcaSlicer cannot slice without a full preset set (exit 205 on bare defaults), so the Orca adapter has no minimal smoke path analogous to PrusaSlicer's. Building and validating the Orca adapter requires sourcing a real Orca printer/filament/process preset triple first; nothing here establishes that Orca's `--export-settings` is deterministic or that its emitted G-code normalizes the same way.

- [lockfile-design] SuperSlicer is not installed on this machine and fullcontrol is not installed. Nothing in this track establishes anything about either adapter. Any claim about a three-engine lock is unverified for the third engine.

- [lockfile-design] Binary G-code cannot be normalized with the proposed text filter (timestamp sits inside a CRC32-checksummed container). Shipping bgcode support means either a container walk or an explicit exit 2 — there is no third option that stays honest.

- [org-fit] Nothing in the proposal is impossible, but one thing is impossible AS STATED: an enum with both `engine_error` and `invalid_profile` as branchable outcomes cannot be computed on PrusaSlicer 2.9.6's partial-preset path, because the engine dies by SIGSEGV with no output at all (exit 139, empty stdout, empty stderr, reproduced 6/6). Either the enum collapses those two, or slicelab must guess — and guessing is the founding rule violated in the drive layer.

- [org-fit] The licence is potentially blocked by a decision the proposal defers. PrusaSlicer, OrcaSlicer and SuperSlicer are all AGPL-3.0 and reached over a process boundary, so per prusaslicer-py D7's reasoning the choice stays open and Apache-2.0 is available. But the proposal names a future 'native' backend over FullControl. If that backend is an in-process import rather than a subprocess, FullControl's licence reaches slicelab and §9's 'take what the engine compels' applies. I could NOT verify FullControl's licence (not installed, no network use attempted) — this is flagged as unverified, and it must be settled before LICENSE is written, not when the backend lands.

- [prusaslicer-py-disposition] Option C is not achievable as stated. prusaslicer-py 0.1.0 is on PyPI as of 2026-09-06T01:39:08Z. PyPI does not support renaming a project's distribution name, and a deleted project name cannot be re-registered. The git history and the GitHub repo name can move; the PyPI name cannot follow. C therefore degenerates into 'B with the history preserved', and it does so while destroying a one-day-old public release the org just announced.

- [prusaslicer-py-disposition] Any option that makes slicelab import prusaslicer-py (option A) contradicts org AGENTS.md §5 ('The stable surface is the artifact and the exit code, never the Python API') and turns a §10 escalate-only decision ('extracting shared code into a common library or framework across members') into an implicit default. It also does not solve the problem it appears to solve: the reusable plumbing is inside a class named PrusaSlicer keyed to PrusaSlicer constants, so option A gives slicelab a PrusaSlicer adapter and nothing at all for Orca.

- [prusaslicer-py-disposition] slicelab cannot be Apache-2.0 and import fullcontrol in-process — fullcontrol 0.1.2 is GPL-3.0 on PyPI. Per org §9 the engine's licence wins where the binding compels it. Settle this before slicelab's first public commit.

- [slicespec-boundary] No off-the-shelf Python G-code parser is a viable dependency for slicespec, and I verified this rather than inferring it. gcodeparser 0.3.0 silently discards all 1392 comment lines including the entire config footer; pygcode 0.2.1 silently misclassifies M104/M221 as spindle speed and cannot see M82/M83 at all (and is GPLv3, unreleased since 2017); GcodeTools 0.3.2's own packaged METADATA declares heavy API churn and 'very large amount of bugs'; pyGCodeDecode 1.5.1 is the only one with real independent physics but reports unsupported commands and default-profile degradation only as log lines (s.unsupported_commands is None). slicespec must own its parser. This is a cost, not an impossibility — a correct scanner covering G0/G1/G2/G3, M82/M83, G92, M221/M220 and the comment channel is a few hundred lines; I wrote a working core in one sitting and it reconciles exactly.

- [slicespec-boundary] I could not produce OrcaSlicer G-code on this machine (2.4.2 requires --load-settings profile bundles; raw profile JSONs failed compatible_printers_condition, return_code -17 / exit 239). Every claim in this report about Orca's G-code footer, metadata comments or config-emission format is UNVERIFIED. slicespec's cross-engine parser scope cannot be finalised until someone slices with Orca successfully.


# Fatal flaws (judge panel)

- P1, CONTRACT VIOLATION, and the sharpest error in the set: `verify` defaults to `--tier config` and exits 0 on success, while P1's own V0 SCOPE text says 'Tier 1 alone passing must exit 2, not 0.' The two halves of the proposal contradict each other, and the CORE SURFACES version is silence reading as success inside the verify verb — a user gets a green for a check that never looked at the artifact. P2 has the correct rule and it must be adopted verbatim: an explicitly requested narrow tier may exit 0 because that is the question asked; a SILENT fallback to a narrower tier exits 2 with `checked` and `not_checked` as fields.

- P1, CONTRACT VIOLATION: 'geometry path absent host-side' is mapped to exit 64 (usage). §2.2 names 'a source file that is not there' as an environment fault by example. A missing input is 4, not 64. 64 is for slicelab's own CLI usage, and conflating the two means a CI job with a bad path reports as an operator typo rather than a broken environment.

- P1, §5 VIOLATION: declaring `slicelab.cli.main(argv: list[str]) -> int` a stable Python surface. §5 is unambiguous — 'the stable surface is the artifact and the exit code, never the Python API.' P2's position (zero exported names, a test asserting `dir()` minus dunders == {'__version__'}) is the faithful one; P1's stable-main is a small crack that becomes the second, weaker interface §5 forbids.

- P2, MEASUREMENT REFUTED AT ITS BOUNDARY: D5 claims `--key=value` works 'for every type' and uses that to delete the need for an option-type catalogue. I tested eleven forms on 2.9.6: int, float, percent, bool, enum, comma list (`--bed-shape=...`), composite (`--thumbnails=160x120/PNG`) and a G-code string all return rc=0 — but `--post-process=` returns rc=1 'No value supplied for --post-process'. Setting a key to EMPTY is not expressible in the `=` form. D5 survives with that boundary stated, and slice.toml needs an explicit answer for 'clear this key' (refuse it, or carry a sentinel) rather than discovering it as a silent no-op. Note the corollary for P1: its `plan.py` says it 'knows which keys are bare booleans (--key=0) vs valued (--key N)' — an option-arity catalogue that P2's `=` form makes unnecessary, and which P1's own D6 (ship no engine-derived corpus) would otherwise force it to generate.

- ALL THREE: run-level `unsupported` folds to exit 1, diverging from netspec D26 which folds it to 2. Three-for-three means it is not a discriminator, but it must be FILED as candidate adjudication A5 and not shipped as a silent choice — §6.3 says the vocabulary follows the tools, not the reverse, and §10 makes changing a released tool's exit code an escalation. P1's route is cheapest: in a vocabulary-free v0 the state is unreachable, so the conflict does not have to be opened at all.

- P2 (D14) and P3 (D16), §10 BOUNDARY: both recommend that the DRIVE layer adopt exit 4 for a missing engine and name orlab as needing to change. The diagnosis is right — orlab's `__main__` returns literal 0 or 1, giving the verify members' 'violated' code for what §2.2 defines as an environment fault, with no DECISIONS entry defending it. But recording that recommendation inside slicelab's own DECISIONS.md is deciding a change to another shipped member. It goes in the A5 adjudication with an owner, not in slicelab's decision log.

- DOSSIER CONTRADICTION that must not propagate: the SuperSlicer track's adversarial check asserts `--query-printer-models` gives 'EXIT=0 with a JSON document'; four other places (and my own run just now) give rc=1 with 6550 bytes of valid JSON and 0 bytes of stderr. All three proposals adjudicate on JSON parseability so all three are safe, but any plan text quoting EXIT=0 is quoting a number nobody produced (§7). Record rc=1, with the command.

- STATUS MAPPING DISAGREEMENT that needs settling before v0, not after: P2 folds a `coerced` key to `refused` (1); P1 and P3 fold it to `incomplete` (2). P2 is right. `--perimeters 4.7` resolving to `perimeters = 4` at rc=0 with zero bytes of stderr is something slicelab ESTABLISHED — it looked, and the intent was not honoured. Exit 2 means 'could not tell', which is false here and tells a user to retry when retrying will never change the answer. `absent` (key nowhere in the readback) is the genuine 2, because we cannot tell whether it was honoured under another name.

- P1, §2.4 GAP: deferring the OrcaSlicer adapter to v0.2 means `test_names_confined` and the whole adapter boundary never observe a second engine's vocabulary. A boundary check whose red state has never been seen is not a check, and P1's central claim — 'you cannot end up with a PrusaSlicer-shaped abstraction if you decline to write the abstraction' — is precisely the claim that only a second implementation can test. The empty-vocabulary test is genuinely strong; the ADAPTER boundary test is not, until engine two exists.

- TRAP TO NOT REINTRODUCE (P1 states it correctly; the final plan must keep stating it): the sidecar / hash-only lock is NOT a licensing measure. The dossier refuted that — the committed part.gcode already carries the same 373-key vendor payload including thousands of characters of verbatim Prusa G-code macros, so a hash-only lock removes zero bytes from the repository. The surviving reasons are diff noise, lock size, and secret hygiene (`--save` emits printhost_apikey in cleartext where the G-code footer strips it). Anyone who reintroduces the licence rationale has reasoned from a refuted premise.

- §4 DEVIATION, uniform and well-argued but still a deviation: all three make slice.toml TOML, with the identical argument (§4 governs artifacts that ASSERT; slice.toml REQUESTS) and the identical honesty test (if slicespec ships YAML contracts, §4 was abandoned by the back door and slice.toml was the wedge). The argument is sound and the constraints (inert parser, closed typed vocabulary, unknown `[set]` key refused at 1) are real mechanism. But slicelab would be the first member to deviate from a section written without qualification, so it belongs in slicelab's DECISIONS.md AND in front of the org, not decided three times over in parallel and treated as settled.

- ALL THREE ship the same broken test. The 'no engine-native option name in a string constant outside adapters/<engine>/' boundary test, as specified, fails on day one. PrusaSlicer's confirmed option surface includes `--output`, `--load`, `--save`, `--info`, `--datadir`, `--threads`, `--slice` — and every proposal's own lock schema uses `output`, `path`, `bytes`, and every CLI module will contain the strings 'save', 'load', 'info'. A zero-intersection assertion against all core string constants is red before the first adapter exists. Scope it to the FFF CONFIG-KEY namespace (the ~411 `--help-fff` keys), not the action/transform verbs, and make the stoplist itself a numbered decision rather than a quietly growing allowlist.

- SHIPPABLE-FIRST prints the word 'sliced' on a run that exits 2. Its own worked example is `$ slicelab slice` → `sliced part.gcode 604407 B ascii 100 layers 24m42s 1 override coerced` → `$ echo $?` → `2`. In a tool whose founding rule is that silence must never read as success, the first token of output must be the outcome word (`incomplete`), never a past-tense verb that reads green to a human skimming CI logs. Fix the renderer and pin it with a test asserting the first token equals the outcome value.

- SHIPPABLE-FIRST is internally inconsistent on the incomplete preset triple. D4 and the outcome table say exit 64 (usage); the `refused` definition says pre-flight refusals on evidence are exit 1. Settle it at 1: the intent file is well-formed TOML, the tool adjudicated a semantic property of the declared request, and 64 is for argv problems. Leaving both in the design means the first user report is about the exit code.

- The three disagree on `coerced` and none of them notices. CONTRACT-PURIST maps coerced → refused (1); SHIPPABLE-FIRST and LONGEVITY-FIRST map it → incomplete (2). CONTRACT-PURIST is right: 'you asked 4.7, the engine resolved 4' is a conclusive negative about the request, not an inability to decide, and exit 2 wrongly invites a retry that will never change the answer. Pick 1, write the reasoning down, and stop the split.

- Orca's flatten.py has no stand-down path, in EITHER proposal that ships it. Both adapters pre-resolve the `inherits` chain because Orca 2.4.2's CLI never does. If Orca 2.5 fixes it, slicelab either becomes redundant or double-resolves, silently. An adapter that works around an upstream defect MUST detect that defect's presence on the installed build during characterisation and refuse rather than apply the workaround blind. As written, both would keep working around a fixed bug and report exit 0 — the org's own founding failure shape, aimed at itself. Same applies to compat.py's `compatible_printers` injection, which is keyed to a 16.7% census that will drift every release.

- CONTRACT-PURIST's D6 rests on D5 before D5 is established. 'Ship no option catalogue' is only safe if `--key=value` works for EVERY option type, and the dossier does not establish that for list-valued or repeated options — its own multi-extruder reproduction used five repeated `--material-profile` flags, which is not a single `--key=value`. K4 names the risk correctly, but the design then treats D6 as settled. Run K4 first; if repeats or lists need a different form, D6 collapses back into needing engine-derived option metadata, which D6 forbids shipping, and there is no third path.

- LONGEVITY-FIRST's vocabulary admission test is not a test. 'Slice the same part on every present engine, vary the key, show the toolpath effect moves in the same direction and magnitude class' has no definition of 'magnitude class', requires every engine installed in CI, and will be either skipped or permanently blocking. Worse, the proposal seeds 5 core keys WITHOUT running it — the admission test failing its own first application. Cut the test or cut the seed keys; shipping both is the vocabulary equivalent of a green check that never ran.

- LONGEVITY-FIRST states '626 keys' for Orca `--export-settings` with no command attached. The dossier's own measurements are 616 (no presets), 624, and 633–635 (with presets) — three different figures for three different configurations. §7 is explicit: every figure carries the command that produced it. A proposal selling exactly this discipline should not restate a number it did not produce, and neither should the resulting DECISIONS.md.

- CONTRACT-PURIST's S1 is not a shippable increment. 'Ships as a tool whose only honest answer is error(4): no engine configured' is a commit, not a release. Do not count it when planning weeks-to-first-release; the real first release is S2 (`doctor`) at the earliest and honestly S3 (`resolve`).

- Nobody budgets for what `[base]` MEANS on Orca. Orca's preset addressing is a different KIND — flattened JSON files supplied by the caller, not names resolved by the engine — so a shared `[base]` table with printer/print/filament names quietly assumes a mapping that does not exist. SHIPPABLE-FIRST sidesteps this correctly by namespacing `[prusaslicer.base]` from the first commit; the other two carry an un-namespaced `[base]` that will need a breaking schema change the day Orca lands. Adopt the namespaced form regardless of which plan wins.

- Not a flaw, but state it in user-facing docs or the name is a lie: every determinism, identity and normalization measurement in all three designs is one host, one Flathub build, one x86_64 CPU. The output-identity half of the lock is a same-machine, same-build equality check until a second machine says otherwise. LONGEVITY-FIRST handles this best by putting `cross_machine_reproducibility_unestablished` in `unknowns` on every lock; whichever plan wins must do the same and have `explain` print it, or 'lock' promises a portability it has not established.
